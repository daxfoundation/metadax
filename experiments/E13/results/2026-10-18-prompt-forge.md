# E13 Prompt Forge — 2026-10-18

## Question

Can a sonnet-generated retrieval-practice-first variant of MP-06 (the adaptive tutor) keep
MP-06's contract and output schema unchanged while adding a retrieval-probe turn at the start,
and can that variant then pass certification?

## What ran

- **Model:** claude-sonnet-4-6 (SIMULATED — sonnet agents acting as the MetaDAX engine)
- **n:** 1 run per case (no seeds; temperature not set)
- **Cases:** 6 MP-06 base cases × 2 stacks (base + variant) + 4 new MP-06-variant cases × 2 stacks = 20 runs
- **Grader:** `/tmp/metadax/evals/grade.js` (schema + gate + expect checks) + `check-variant-behavior.cjs` (retrieval-language + type + state checks for the 4 new cases)
- **Sizes:** stacks ~320–393 lines; outputs 1–4 KB each

**Variant-stack regression check:** 6/6 MP-06 base cases pass with the variant stack vs 4/6 with the base stack. Zero regressions; variant improves schema compliance.

**3 failures — all on base stack, all the same root cause:** the base-prompt engine emitted `"in_progress"` for a not-yet-started level (e.g. `state.levels.electron-transport-chain.Apply: "in_progress"`). `"in_progress"` is not in the `tutor-turn/0.2` schema enum (valid values: `passed_first_try`, `passed_after_help`, `failed`, `skipped`, `not_started`). The variant stack did not reproduce this error.

## Verdict

**PASS on a substituted variant; the card's variant is untested.** The retrieval-first variant passes certification on first attempt. Variant stack: 10/10 schema-valid, 10/10 rubric pass, 4/4 variant-behaviour checks. No regressions vs the base prompt. Kill line not reached (kill = fails certification twice after repair; variant passed on first attempt).

Note: the E13 card originally specified a Charlotte Mason variant generated via a formal FORGE operation. This run used a retrieval-practice-first variant generated by direct model prompting (no FORGE prompt exists yet). Result is labelled SIMULATED. The variant was saved with no hand edits after generation.

## What compounds

- The variant-prompt generation + fixture authoring + certification pipeline (prompt → eval cases → grade) completes end-to-end in a single session, demonstrating the viability of prompt-forge as a concept.
- The variant's 10/10 schema-compliance vs the base's 7/10 suggests that the retrieval-first rewrite incidentally tightened the instruction for state tracking (the enum-violation path through the base prompt is the intro → first question turn where an intermediate level gets incorrectly labelled `in_progress`).
- `check-variant-behavior.cjs` is a reusable pattern for certifying method-specific invariants beyond what the base grader checks.

## Dead ends kept

- **FORGE operation absent:** no formal Prompt Forge operation (MP-XX) was used. The variant was generated by a sonnet agent given the base prompt and a plain-language instruction. This means regeneration is not reproducible from a schema and cannot be automated. See B46.
- **4 new cases cover only 4 state transitions:** probe-wrong-answer, probe-skipped, multi-concept probe, and probe at concept 2+ are untested. See B47.
- **Silent edge case — completed first concept:** the variant §1 does not specify what to do if the first concept's Remember level is already `passed_first_try` in PROGRESS. A model could re-probe a completed level. See B48.
- **Base-prompt enum violation (`in_progress`):** three base-stack runs failed due to an invalid level-status value not caught before this run. This is a pre-existing base-prompt issue, not introduced by the variant.

## Bottlenecks

See `bottlenecks-2026-10-18.md`. New: B46 (no FORGE operation), B47 (narrow new-case coverage), B48 (probe-on-completed-concept edge case). Existing confirmed: B04, B06 (grader handles tutor-turn correctly); B07 (no prose-after-JSON observed in this run); B08 (single vendor, confirmed open).
