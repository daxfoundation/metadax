# E04 run record -- 2026-10-09

Automated: a model answered each case and a deterministic grader scored the replies. No person took part. This is not a certification.

Written 2026-10-20 from the run notes (the maintainer's working notes, not published) and the saved model replies, which are committed beside this file in `2026-10-09-raw/`. The run was not recorded in this repository when it happened; this file closes that gap. `2026-09-27-first-run.md` stays as written: it records an earlier attempt that did not reach a model.

## Outcome

- **Run 1** (19 of the 27 cases): 12 pass, 7 fail.
- **Run 2** (15 cases: the 7 failures and 8 cases run 1 had not covered), after a grader fix and a prompt edit: 11 pass, 4 fail.
- Every one of the 27 cases ran at least once. No single run covers all 27.
- The card's stop rule is "kill (block release) if any operation is under 90 percent schema-valid on a primary model". Read literally it would fire: after run 2, MP-02 is at 0 of 2 and MP-04 at 1 of 2. Of those three failing cases, two fail because the suite's own `expect.schema` setting points at the wrong schema, not because of the model.
- One vendor's model only. The card asks whether the prompts pass on two vendors. That question is not answered.

## Method

- **Suite.** The 27 cases in `evals/cases/` as committed at `fee91e8`: MP-01 (3), MP-02 (2), MP-04 (2), MP-05 (12), MP-06 (6), MP-07 (2). Each case has a `stack.txt` (the exact prompt), an `input.json` and an `expect.json` (the rule the grader applies).
- **Model.** Claude (Anthropic), alias `sonnet`, as the run notes record it. The exact model id was not recorded, so none is given here (`docs/ACCURACY.md`, item 8). The notes record no temperature or seed.
- **Running.** Each case's `stack.txt` was handed to a fresh subagent, one case per subagent, with nothing else. The reply was saved to a file named `<operation>-<case>.md`. This is a subagent run, not the committed runner (`evals/run_claude_p.js`) and not the promptfoo matrix. The notes do not say whether a subagent had tools or instructions beyond the case.
- **Grading.** `evals/grade.js`, deterministic, four layers in order: parse (exactly one JSON object), schema, the `docs/INTERFACE.md` gates (ids only from REGISTRY and PATH, and so on), then the case's `expect.json`. A case passes only if every layer passes. No LLM-rubric score was produced, so the card's rubric metric has no value from this run.
- **Run 1 harness.** The repository as committed at `fee91e8`, the last commit before the fix below. `grade.js` is blob `b6f20ab`.
- **Run 2 harness.** The same, with two changes made after run 1:
  1. `grade.js` now unwraps the operation-output envelope before schema validation. An operation returns its file object inside an envelope (`{"type":"profile","profile":{...}}`; `prompts/SCHEMAS.md` section 9 lists `metadax.learner`, `metadax.course` and `metadax.node` as persisted file objects, "not operation outputs"), and run 1's grader had validated the whole envelope against the flat file schema. It also checks a `"type":"error"` reply against `error.schema.json` when the case's `expect.type` allows `error`. The notes decided the prompts and `SCHEMAS.md` were already right and the grader was wrong. The grader change is `2026-10-09-raw/run2-grade-fix.diff` (`grade.js` blob `b6f20ab` to `240372b`).
  2. The MP-01, MP-02, MP-04 and MP-05 prompts gained one instruction: return exactly one JSON object and nothing after it. The `stack.txt` files were rebuilt from the edited prompts; per the notes, run 2 used those. The rebuilt stacks were not kept, only the replies.

  Both changes landed on `main` in a later form in `487b7ed` (v0.3), which also changed the id scheme. `main` therefore does not reproduce these verdicts; `fee91e8` does (see Reproduce).

## Reading the four run 2 failures

- **MP-02 design-size-short: a miss by the model.** 66 schema errors. 64 are id-pattern violations: the ids carry a `course:`, `lesson:` or `concept:` prefix (for example `lesson:L01`, `concept:light-energy`), which breaks `^[a-z0-9]+(-[a-z0-9]+)*$` and the lesson, module and objective patterns. The other 2 are titles over 80 characters.
- **MP-02 suggest: a suite error.** `expect.schema` is `metadax.course/0.2`, but a `suggestions` reply (keys `level`, `parent_id`, `items`, `new_concepts`, per `prompts/SCHEMAS.md` section 9) is not a course file, so every course-required key is reported missing. The reply was never checked against the right schema. This failure says nothing about the model.
- **MP-04 render-for-learner: a suite error.** The same mistake: `expect.schema` is `metadax.node/0.2`, and a `rendering` reply is not a node.
- **MP-06 hint: a fixture and model mismatch.** The reply is a tutor-turn `error` saying the session had already ended with a summary turn (`next_action` "done"), so there was no active question to hint on. The case's rule wants `feedback`. Whether the fixture or the model is at fault is a judgement; the grader's verdict is a fail.

## Regrade: what the grader fix does on its own

Run 2 re-sampled the model on edited prompts under an edited grader, so its improvement over run 1 mixes three things. To separate one of them, the run 1 replies were graded again on 2026-10-20 with the run 2 grader. This is a regrade of saved replies, not a new run.

- Now pass: MP-01 adult-create-from-description, MP-01 minor-create-from-description, MP-05 empty-input. Run 1 total on this grader: 15 of 19.
- Still fail: MP-02 design-size-short (`lessons[2].modules[1].objectives[1].title: longer than maxLength 80`), MP-04 generate (`core.key_points_updated: additional property not allowed`), and the two MP-05 parse failures, unchanged.

So the envelope fix alone explains the three profile and error-object results. The MP-04 pass in run 2 comes from a different sample of the model, not from the grader.

## Notes on the record

Where the run notes and the saved replies differ, this file follows the saved replies.

1. **The two parse failures are not trailing prose.** The notes call MP-05 depth5-end-of-chain and over-500-char-input "trailing text after the JSON object". In the saved files, the text after the first object (position 6709 and 6552) is the rest of the same answer (`,"seeds":[...],"rendering_md":...,"options":[],"warnings":[],"missing":[]}`), so the braces are unbalanced earlier: the `node` object closes before its last fields, and the first top-level object ends at `superseded_by`. The strict one-object parse fails either way. The bottleneck register's wording for B07 ("appended prose") does not match these files.
2. **B05 was not shown to be hidden by B04.** The register says the id-prefix miss was "hidden until the envelope fix exposed it". The run 1 MP-02 reply uses bare ids (`course-photosynthesis-intro`); the prefixed ids first appear in the run 2 reply. What the two replies show is two different schema failures from two samples.
3. **One run 2 file is not verbatim.** `run2/MP-04-generate.md` is an archive copy: its `rendering_md` field holds a placeholder sentence saying the prose was elided for length. The pass verdict reproduces on this copy; the original reply was not kept.
4. **The notes' prose glosses are not the grader's rules.** The notes describe some passes in words ("all concepts named, 8 commands listed"). The grader does not check that, and this file does not repeat it; the rules quoted above are the committed `expect.json`.
5. **A third pass is not counted.** The notes describe a third pass the same day (the two MP-02 cases against staged v0.3 prompts). Its replies were not saved, so no result from it is published.
6. **Numbering.** "Run 1" and "run 2" here are the first two runs of 9 October, as in `experiments/BOTTLENECKS.md`. `2026-10-18-cert3.md` is a separate run; it calls itself certification run 3.

## What this does not show

- **Nothing about two vendors.** One vendor's model, one alias, no exact id. Any claim that the v0.2 prompts pass on both vendors is unfounded.
- **Nothing about variance.** One sample per case per run; no repeats.
- **Shape, not quality.** The grader checks that a reply parses, validates, passes the id gates and meets `expect.json`. It does not judge whether a lesson is correct or well taught.
- **Not the card's design.** No floor model, no promptfoo matrix, no run on a pull request, no LLM-rubric score.
- **Not a clean comparison.** Run 2 is a different harness (see Regrade) and, for 8 cases, the only run.

## Reproduce

Regrading needs no model.

```sh
git clone https://github.com/daxfoundation/metadax && cd metadax
cp -r experiments/E04/results/2026-10-09-raw ../e04-raw    # the replies and the grader diff, from main
git checkout fee91e8                                       # the harness before the fix

# run 1: the harness as committed
node evals/grade.js --case evals/cases/MP-05/sibling-reuse \
  --out ../e04-raw/run1/MP-05-sibling-reuse.md
# prints one JSON line; the exit status is non-zero on a fail

# run 2: apply the grader change first
patch -p1 < ../e04-raw/run2-grade-fix.diff
node evals/grade.js --case evals/cases/MP-01/adult-create-from-description \
  --out ../e04-raw/run2/MP-01-adult-create-from-description.md
```
